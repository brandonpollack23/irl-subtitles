# UI localization

The app's own text (phone UI, glasses UI, exports) is translatable (irl-subt-0n7). English and Japanese ship;
English is the source of truth. Spoken-language work (language ID, per-language model routing, code-switching)
is a separate track: plan.md §15 _Multi-language support_. The recording language (`Settings.language`) and the
UI language (`Settings.uiLanguage`) are independent.

## Desk spike (irl-subt-0n7.1, 2026-09-15)

Sources: `@evenrealities/even_hub_sdk` 0.0.15 typings and README, `@evenrealities/evenhub-cli` 0.1.14 app.json
validation.

| Question | Finding |
| --- | --- |
| Host locale from the SDK | None. `getUserInfo()` returns `uid`, `name`, `avatar`, `country` (a country, not a language); `getDeviceInfo()` has model, serial and status only. The UI language comes from `navigator.languages` in the WebView, with `country` unused (Japan ≠ Japanese). |
| Menu label limit | `itemName` max 32 UTF-8 bytes, validated by the SDK before calling native (an invalid menu is rejected, not truncated). Japanese is 3 bytes per character: 10 characters, so labels are written short and tested against the budget. |
| `supported_languages` | The CLI accepts `en, de, fr, es, it, zh, ja, ko` (lower-cased). Adding `ja` is valid for packing. No field localizes the permission `desc` (one string, max 300 characters), so it stays English. |
| G2 CJK glyphs | Not answerable at the desk: the SDK ships no font and documents no glyph coverage. The SDK's own docs are bilingual (README.zh-CN), and text containers take arbitrary UTF-8, which suggests CJK rendering, but kana and kanji on real firmware are verified on device in irl-subt-0n7.10. If glyphs are missing, the fallback is keeping the glasses in English while the phone is Japanese (a follow-up, not built). |
| Grapheme safety | `truncateUtf8` cuts on code points, which never splits a kana or kanji but can split a combining sequence or emoji ZWJ sequence; it now cuts on grapheme clusters via `Intl.Segmenter` where available. |

## Design

- `@irl/i18n` (no Solid dependency) holds the catalogs, locale resolution and formatters, so the glasses controller,
  the Markdown export and the phone UI share them.
- `en` is the source catalog. `Messages` is its type; `ja` must satisfy it, so a missing Japanese string fails
  `pnpm typecheck`. Parameterized strings are functions.
- Packages don't produce English sentences for the UI: they return codes (option blockers, lock reasons, data flow,
  degraded reasons, key test results, match failures, user-facing error codes) and the UI renders them. English text
  that only reaches logs, diagnostics or the LLM prompt stays in the packages.
- The phone UI re-mounts when the language changes, so every string follows without per-component reactivity; the
  hash route keeps the user on the same screen. The glasses page rebuilds.
- Stays English: model display names and technical model notes (proper nouns and benchmark notes), device
  availability details from the model catalog, raw error details from services and runtimes (shown after a
  localized lead-in), the Evaluation (voice tuning) view, the dev platform marker, diagnostics logs, and the
  app.json permission description.

Register: です/ます for sentences, plain noun phrases for buttons, menu items and headings. Latin names (Soniox,
Speechmatics, model names) are separated from Japanese by a space; full-width brackets （） and quotes 「」 wrap
Japanese text.

needs a fluent reviewer before a Japanese release (irl-subt-0n7.11).
